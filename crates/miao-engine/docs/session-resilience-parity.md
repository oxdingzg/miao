# Session resilience parity gate

These contracts apply to both execution backends. TypeScript implementations do not automatically change the Rust engine. Passing the original M0/M1 inventory or compilation alone does not establish parity with subsequently added Session behavior.

## Required cross-backend scenarios

| Contract                     | Required observable result                                                                                                                                                                                                                                                                                 | Current evidence anchor                                                                                                                                    |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Invalid local tool arguments | An unexecuted local call with invalid JSON may be corrected at most twice. A previously completed file write happens once. The final successful continuation is successful, while intermediate errors remain visible. Provider-executed calls and unknown side effects are not replayed.                   | TS #614; `packages/miao/test/cli/run/tool-input-recovery.test.ts`. Rust parity not yet verified.                                                           |
| Argument generation budgets  | Bound unfinished arguments by UTF-8 bytes and elapsed generation time, including a stalled stream. Cancel before incomplete local dispatch. Preserve completed operations. Do not automatically replay a budget violation or apply the deadline to tool execution.                                         | TS proposal #615; `packages/miao/test/cli/run/tool-input-budget.test.ts`. Rust parity not yet verified.                                                    |
| Transport interruption       | A retryable abnormal close can resume over committed history within a bounded allowance. Partial output and completed tools remain observable; completed mutations are not repeated. Protocol/policy failures remain terminal.                                                                             | TS #590; provider and Session regressions. Rust transport/recovery parity requires end-to-end verification.                                                |
| Background completion        | A job completing after its Session becomes idle admits a durable completion notification, promotes it, and starts the next provider turn without a new human prompt. No lost wake or duplicate execution during completion/idle races.                                                                     | TS #610; actual compiled HTTP/model verification and `session-runner.test.ts`. Rust notification/ownership path requires corresponding verification.       |
| Dependency-ready work        | Stable task IDs and prerequisite edges survive reload. If 4 waits, 5 depends on 4, and 6 depends on 5, independent 7–9 remain runnable. Completing 4 unlocks only 5; completing 5 unlocks 6. Cancelling a prerequisite does not satisfy it. Invalid graphs are rejected without replacing prior state.     | TS proposal #618; `session-todo-dependencies.test.ts` and actual CLI continuation tests. Rust state/tool schema and scheduling parity not yet implemented. |
| Authorized idle continuation | Ready work continues within existing step, iteration, and no-progress limits only under explicit autonomous authorization or configured looping. A waiting-only graph, including its pending locked dependents, becomes idle without polling. Paused, blocked, or done goals stop autonomous continuation. | TS proposal #618; Core and actual CLI tests. Rust parity not yet implemented.                                                                              |
| Client status projection     | A Session with ready unfinished work must not be represented as globally waiting merely because another task waits. Waiting-only dependency graphs, runnable tasks, completed work, and missing decisions remain distinguishable across transcript, sidebar, and terminal status reports.                  | TS #618 tests in `packages/tui/test/session-state*.test.*`. Both backend adapters must satisfy the same client contract.                                   |

Issue and PR references above describe evidence or proposed changes, not an assertion that those changes are all published. Check the merged revision and actual executable under evaluation.

## Verification boundaries

- Use the same task graph, initial workspace, provider fixtures, and explicit side-effect oracle for both backends. Do not treat either implementation's accidental behavior as the specification.
- Include failures and attempted correction/continuation turns in usage, latency, and resource measurements. Unknown usage stays unknown.
- Verify native state admission and execution, not just an adapter that rewrites Rust output into an expected TypeScript shape.
- Keep Session execution ownership singular. A facade, external timer, background job, or notification must not introduce a second execution authority.
- Preserve exact retry identity, strict tape consumption, and unknown-side-effect handling. No live-I/O fallback or relaxed replay comparison may manufacture a passing result.
- Verify durable reload, provider turn boundaries, and real client delivery. Headless replay alone does not prove HTTP/TUI product readiness.

The default-backend switch remains gated on these scenarios, the existing ownership/protocol gates, fixed quality and efficiency measurements, and installation/rollback acceptance. Pending contracts must be recorded as gaps rather than marked complete from CI or a source-level resemblance.
