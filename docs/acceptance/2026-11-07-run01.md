# Acceptance record — RUN-01 input receipts, steer/queue and exact retry

Item: `RUN-01`. Tree: `17c6feb84a`. Commands ran on the macOS build host
(`aarch64-apple-darwin`, cargo 1.99.1) from `crates/miao-engine` on that tree.
The suites are store/runtime level: a real SQLite ledger, a scripted provider,
no network.

## Where each state the issue names lives

The durable ledger begins at admission; "sent" is the client's optimistic state
before the engine acks and is not a ledger state. One row in `engine_input` plus
the event that settled it answers "where is my prompt now":

| issue word | ledger answer |
| --- | --- |
| admitted | the `input.admitted` event and the `engine_input` row, state `pending` |
| pending-promotion | `pending`, with `pending_ahead` counted inside its delivery class |
| executing / failed | deliberately not on the receipt: promotion starts a run whose outcome belongs to that run (`engine_run.state`, one active run per Session); the TUI projects that run state, not a receipt state |
| steer/queue marks | the `delivery` column, carried verbatim onto every receipt |

`input_status` reports `state`, `delivery`, `admitted_seq`, and per state:
`pending_ahead` for `pending`, the promoted message's seq and run checkpoint for
`promoted`, the `input.cancelled` event for `cancelled`, and `unknown` for an
input that belongs to another Session. An unknown Session id is an error, not a
receipt.

## A server-side retry of a durable identity creates neither a duplicate message nor a duplicate call

> A server-side retry of a durable identity creates neither a duplicate message nor a duplicate call

`admit_input` reconciles an exact retry: the same session, prompt, delivery,
attachments, command and agent references return `duplicate: true` with the
original `admitted_seq` and append no second event; any difference is a
conflict, and a cancelled identity stays dead.

## Queued messages are promoted only at a safe boundary, and order is restored after reconnection

> Queued messages are promoted only at a safe boundary, and order is restored after reconnection

The serialized drain promotes pending steer inputs at tool boundaries and one
queued input at the idle boundary. The runtime test asserts the ordering
directly: the steer text arrives in the next provider turn while the queued
text stays pending, the queued text arrives only after the run settles, and a
re-admitted identity after completion reports `duplicate` with no turn within
100 ms.

| criterion | command | observed |
| --- | --- | --- |
| steer at tool boundary, queue at idle, retry runs nothing again | `cargo test --locked --test runtime` | `test result: ok. 5 passed; 0 failed` |
| reconnect reads the inbox oldest-first with an `after` cursor | `cargo test --locked --test store` | `test result: ok. 22 passed; 0 failed` |

## What this record does not cover

- **"sent"** is a client-optimistic state; the ledger has no opinion about it,
  and this record does not pretend the composer is evidence.
- **A live reconnect against a real server** — a TUI paging a dropped socket —
  is a product-acceptance run, not an offline batch; the store-level cursor
  paging here is the engine half of that behaviour.
- **Multiple clients paging one inbox concurrently** is not exercised.
