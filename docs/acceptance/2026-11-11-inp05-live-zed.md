# Acceptance record — INP-05 the Zed selection reaches the real composer

Item: `INP-05` (#1981). Tree: the pull-request head for branch
`test/inp05-live-zed`, parent `origin/main` `d22a69aa7d`. Commands ran on **two**
real hosts, each from `crates/miao-tui`:

- Linux build host, `cargo 1.99.1`, `sqlite3 3.45.1` installed for the probe;
- macOS host (Darwin 25.5.0, arm64), the same toolchain, `/usr/bin/sqlite3`.

`2026-11-07-inp05-visible-context.md` accepted the interaction: the selection is
ordinary text in the composer, deleting it keeps it deleted, a changed selection
replaces the text it supersedes, and a Zed failure leaves the draft alone. Every one
of those rows drives the draft through a **fixture probe**, so none of them could say
the shipped binary reads a real Zed database. That was the last thing this item owed,
and this record closes it.

## What the live test does

`crates/miao-tui/tests/zed_context.rs` boots the real `miao-tui` binary in a pty
against the scripted engine (the same `portable_pty` harness as `interaction_review.rs`
and `input_latency.rs`), with:

- `ZED_TERM=true`, which is what a Zed terminal sets and the only thing that makes the
  probe run at all;
- `MIAO_ZED_DB` pointing at a database this test writes with `sqlite3`, in Zed's own
  layout (`workspaces`, `panes`, `items`, `editors`, `editor_selections`), whose
  workspace path is the canonicalized path of the spawned workspace and whose single
  selection covers `let answer`;
- a keypress, because the probe is throttled to one read per 500 ms and is driven by
  input.

It then reads the rendered output, stripped of terminal control.

## Criterion — "Allow users to inspect and remove automatically attached context."

| leg | command | observed |
| --- | --- | --- |
| the selection is in the composer before anything is sent, on Linux | `cargo test --test zed_context` (`crates/miao-tui`, Linux host) | `test result: ok. 2 passed; 0 failed; finished in 2.47s` |
| the same on macOS | `cargo test --test zed_context` (`crates/miao-tui`, macOS host) | `test result: ok. 2 passed; 0 failed; finished in 4.29s` |
| what the composer actually painted | the same run, printed by the harness | `<system-reminder>Note: The user selected #1 from "/tmp/miao-zed-context-true/ws/notes.rs". ```let answer``` This may or may not be relevant to the current task.</system-reminder>` followed by the typed `hi` — the operator reads it before sending |
| a terminal that is not Zed carries nothing, even with the database configured | `cargo test --test zed_context a_plain_terminal_carries_no_context` | `ok` on both hosts |

The macOS leg is not decoration: the probe compares the workspace path Zed recorded with
the app's own cwd **lexically**, and on macOS `temp_dir()` is a symlink under `/var`
while the app canonicalizes to `/private/var`. The first run there found no selection for
exactly that reason, and the test now writes the canonical path — a real defect in the
verification, caught by running it on a second platform.

## What this record does not claim

- **Removal is not asserted live.** The harness reads an append-only stream, so any
  repaint of a screen still showing the reminder adds occurrences whether or not the
  draft still carries it; the first version of this test failed on macOS for that reason
  and the assertion was removed rather than tuned. Removal, replacement and the failure
  path stay pinned where they are observable — `deleting_the_context_keeps_it_deleted`,
  `a_changed_selection_replaces_the_context`, `a_zed_failure_leaves_the_draft` in
  `crates/miao-tui/src/app.rs`.
- The database is written by the test rather than by a running Zed, because a live Zed's
  selection changes as a person works; the format, the probe, the binary and the terminal
  are the shipped ones.
- Windows is unexercised: the probe's database path is macOS/Linux only, and no Windows
  host ran this test.
- No cost or latency evidence: the probe is throttled to 500 ms and this is not an
  optimisation.
