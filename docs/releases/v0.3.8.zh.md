# miao v0.3.8

v0.3.8 让新会话默认生在引擎上，并把这套 TypeScript runner 早就具备的能力一并接过来：过去只能经宿主 loopback 网关的几家 provider 现在各走原生 wire，被拒绝的工具调用会说清是哪个字段不对，长会话保住最新的消息，而仅仅"连不上"的端点会报成不可用，不再伪装成请求写错。本版本不改变任何既有会话的属主。

## 引擎与 native 会话

- **新会话默认由引擎拥有。** 属主原本取决于是否配置了引擎存储根；服务端现在提供默认根 `<data>/engines`，于是新会话默认属于引擎，除非操作者用 `--engine ts` 显式回滚 —— 它仍然设置空的 `MIAO_ENGINE_STORAGE`，不会落到默认根。已被 TypeScript 拥有的会话保持自己的路径不动。
- **剩下的 TypeScript 会话可以一次整体迁移。** `miao session migrate-all` 先规划再执行：没有绑定模型、或读不到产品行的会话会被跳过并汇报，而不是中断整批；随后逐条走既有的可续跑协调器（frozen → prepared → switched → completed），失败会汇总并以非零退出。重跑是安全的：已完成的导入是 no-op，中断的导入从上次持久状态继续。
- **长会话保住尾部。** 快照投影与 provider 历史选择都停在 1001 条消息，而文档中真正的失控上限是 20000 条，于是超过这个点的会话会丢掉最新的历史，fork 只复制前缀，模型看不到最近的提示词与工具结果。现在两者都多读一行越过真正的守卫，超大的历史会显式失败而不是悄悄截断。
- **被旧引擎截断的快照会被拒绝。** 0.3.7 及更早的引擎用 `LIMIT 1001` 投影，游标却声称覆盖整个会话，于是长会话的尾部在 TUI 里凭空消失。这种快照现在以 `engine_snapshot_truncated` 明确拒绝，并提示把 miao 升级到 0.3.8 或更新，而不是展示一个停在 1001 行的尾部。
- **回合只在空闲确认之后才被宣布结束。** native 无头运行可能在引擎仍在执行时就报告成功并退出，引擎随后把这次 run 记为 interrupted：等待在"输入提升"与"run 行写入"之间返回了。显式等待者现在会先确认一次已稳定的空闲。
- **初始提升与 run 行在同一事务里提交。** 在这两次提交之间取快照，会看到既没有待处理输入、也没有活跃 run，短命的 CLI 因此会在仍在执行时关闭。
- **最后一个允许的回合以收尾结束。** 用完最后一个 provider 回合原本是硬停，长任务因此在半途结束；现在该回合只发文本、收回工具面，转录以"做了什么、还剩什么、下一步是什么"收尾。
- **monitor 只以一条可读通知收敛。** 终止的 monitor 会把整个内部信封序列化成提示词投入，随后又投入一条通用的"去读存储结果"通知，而那个结果只是 `{"exit_code":0}`。现在只收敛一次，内容就是操作者看到的那些行。
- **catalog 读取不再拉起引擎。** 列出历史 native 会话时，可能要为了读标题而按存储各开一个长期引擎。新增的有界只读批量命令承担 catalog 读取，不做迁移、不建 runtime、不领租约、不启动 provider/LSP/MCP；显式选择旧引擎的场景保持原路径。
- **带 todos 或 goal 的会话不再因预算报废。** 引擎把持久进度作为 note 注入，当历史加 note 超过请求预算时直接拒绝回合，而每次重试发的是同一个超大请求。note 只是可选上下文，接近预算的输入现在不带它照常执行。
- **重复输出会在流中途被拦下。** 模型在短散文或推理句上打转时原本会跑到回合预算为止；产品里的检测器现在进入引擎，代码块、表格、列表与非散文字符集等例外保持与产品一致。

## provider 与传输

- **五类端点有了原生 wire。** Bedrock Mantle（Responses，两个 safeguard 模型走 Chat）、Azure OpenAI Chat 与 Azure OpenAI Responses（`api-key` 加显式 `api-version`）、Vertex Anthropic（`streamRawPredict` 形状：模型在 URL 里、body 带 `anthropic_version`）与 Vertex Gemini（OAuth bearer）现在和其它路由一样从同一份路由目录分派。只持有 Entra 或 ADC 凭据的账号仍走 loopback 网关，因为引擎没有铸造这类 token 的来源。
- **路由层传输失败会报成不可用。** 路由器会包裹每条路由的错误，而这个包裹对象此前漏过了运行时的可用性判定，于是一个连不上的端点被报成 `invalid request: provider transport failed`，把操作者引去寻找并不存在的请求格式问题。现在报 `provider unavailable: …`，并可以回退。
- **"不可用"与"请求被拒"是两种错误。** 传输失败、不可重放的响应与可重试的 HTTP 429/5xx 渲染为 `provider unavailable`；真正的 4xx 拒绝仍是 `invalid request`。
- **重试策略与产品的 runner 一致。** 引擎改为在 60 秒窗口内重试，而不是固定次数：500 ms 起、1.7 倍退避、上限 5 秒、±20% 抖动，且不短于 provider 自己给出的暂停；`Retry-After` 的毫秒、秒与日期三种形式都认，最长 15 分钟；另有一次自愈。
- **没有 finish reason 的 Chat 流也能正常结束。** 有些网关只发 `[DONE]` 就关闭；流既然声明自己完整，缺失的 reason 现在按自然结束处理并保留它携带的工具调用，而真正不支持的 reason 仍会点名。
- **空闲期限贯穿整个流。** 读流器原本在第一个语义事件之后就关掉事件期限，于是 keep-alive 字节可以让一个回合永远"忙碌"；现在语义事件会重置滚动的事件空闲期限，ping 不算数。
- **网页搜索保留操作者的 provider 选择。** 产品侧开关 `MIAO_WEBSEARCH_PROVIDER` 会映射到引擎的变量；两者同时存在时以引擎自己的设置为准。

## 工具与失败

- **被拒绝的工具调用会点名字段与取值。** 引擎侧的所有拒绝原本都渲染成同一句 `invalid tool input`，模型分不清是字段名写错还是取值越界，于是原样重发同一次调用。拒绝现在带上原因。
- **产品会读取模型真正发出的输入。** 写成字符串的数字、超出上限的 timeout、以及 edit/write 常见字段别名都是无歧义的，现在直接读懂并执行，而不是拒绝后等模型重发。
- **内置工具保留拒绝原因。** `apply_patch` 与 `todowrite` 原本对所有失败都回同一句话，掩盖了匹配器找不到的行、以及挡住改动的校验或权限规则。
- **shell 结果携带引擎的拒绝。** 被拒绝的调用与被信号杀死的命令都会投影成 `[command not executed]`，而失败调用把原始 JSON 当作消息渲染；现在转录里显示拒绝本身与 `[killed by signal N]`。
- **附件按产品的方式送达模型。** 所选 wire 无法内联的 PDF 会被写到 `.miao/attachments` 并以路径引用；附带的目录与 `@file#10-20` 行范围会以内联文本呈现（目录上限 200 项）；内联文本文件变成 `<file name path>` 块，截断在 10 万字符。`miao run --file` 不再吞掉后面的提示词。

## 上下文

- **剪枝是持久、可读的事实。** 仅作用于请求的工具输出剪枝过去只留下瞬时进度，重连后没人知道删了什么、省了多少。每次剪枝现在提交一条带 fence 的事实，记录受影响的载荷与前后/节省的 UTF-8 字节，产品把它重放为转录里的结算记录。
- **剪枝不会让请求变大。** 接近预算的输出在加上标记与召回说明后可能更长；现在如果替换不能真的省字节，就保留原文，并且标记计入剩余请求大小。
- **app 画出输入构成的估计。** 每个已加载的检查点贡献一份 system/user/assistant/tool/other 的堆叠估计，计算时排除响应自身，并在压缩点重置归因；它与持久快照并列展示，并明确说明不是持久快照的替代。

## 外壳、app 与 CLI

- **输入框用横线框住。** 全宽横线取代左侧 accent 竖条与渐隐条，上下两条沿用 agent 配色。
- **自动批准与 esc 动作显示在输入框下方。** 会话路由原本没地方说明自动批准是否开启、以及回合结束后后台工作是否仍在跑；现在常驻一行提示把两件事都说清楚。
- **native argv 命令按命令渲染。** `run_command` 调用原本只投影参数数组，缺了转录与命令消费方要读的字符串，命令在详情里看不到。
- **`/clear` 保持模型不变。** 新会话原本只带 footer 的本地选择，而 native 会话没有本地选择 —— 它的模型是操作者绑定的路由 —— 于是操作者的默认路由悄悄接管。现在会把当前会话的路由（含 variant）带进新会话。
- **终端关闭不再算崩溃。** 向已被管道关闭的 stderr 写入会抛未捕获异常，让一次本来干净的运行被记成崩溃；关闭与 CLI 输出现在尽力写入。

## 构建、CI 与发布

- **发布产物内嵌为它构建的引擎。** 发布流水线原本只构建引擎 sidecar 却不内嵌，旧版更新器可能保留一个未标记的引擎，从而错过该版本的全部 Rust 修复。现在每种架构的引擎都会先构建、签名，再内嵌进对应 CLI 才发布。
- **conformance 脚本从操作者的数据库起步。** 每个单元格原本从全新的产品库开始，以操作者登录为键的 provider 因此无法解析，所有单元格都在引擎被调用之前就失败。现在单元格以发布渠道的数据库为种子，回落到 dev 渠道。

## 验证与边界

每项改动都通过 `guard` 与聚合的 `ci-gate` 套件，包括 macOS 与 Linux 上的 Rust 引擎测试、TypeScript 单元/类型检查/e2e、会话黑盒回放以及 conformance harness。

- Windows 引擎与运行时套件对着发布提交运行，而不是每个 PR 都跑，所以只在 Windows 出现的问题会在发布闸门暴露。
- Azure 与 Google 的 Entra / ADC-only 凭据仍走 loopback 网关；原生路由覆盖的是引擎能铸造或读取的凭据来源。
- 新会话已默认由引擎拥有，但引擎库还不是唯一权威：产品库仍保有投影，迁移既有会话是一条显式命令。
