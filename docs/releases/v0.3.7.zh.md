# miao v0.3.7

v0.3.7 主要让 native 引擎学会放手：被遗弃的引擎会被释放，而不是被 supervisor 巡检一次次复活；空闲引擎不再被别的进程的工作拖着不放；catalog 与 peer 读取只带元数据、不再传输历史；引擎真的丢了就报成失败回合而不是挂住；长时间的前台命令也不再被 2 分钟上限拦下。外壳这边接上引擎真正落盘的东西 —— 引擎自己产生的通知与提交的提示词共用同一个 inbox 身份、会话列表回到当前目录/项目的范围、运行行收成一行 —— 单文件构建也开始内嵌与它配对的引擎。

## 引擎与 native 会话

- **被遗弃的引擎会被释放，而不是被复活。** 每 60 秒一次的 supervisor 巡检会无条件重新领养每一个已死引擎，于是空闲 15 分钟自我回收的引擎一分钟后又会被拉起，循环不止，每一轮都生成新的 LSP/MCP 子进程 —— 有一个窗口因此积到 68 个活着的引擎。现在只有死掉子进程上一次探测显示仍挂着定时器时才会重新领养。外壳非正常退出时，引擎里的 Unix 宿主死亡看门狗会轮询父进程 pid 并干净地退场，回收 kill-on-drop 的子进程，而不是等一个永远到不了的 stdin EOF（LSP/MCP 继承了管道写端）；Windows 仍以空闲回收作为兜底。
- **空闲引擎被释放，而不是被别的进程的工作拖着不放。** 空闲判定原本查询共享引擎数据库里的每一条 running 行，于是别的进程拥有的工作、或者没人认领的崩溃残留，都会让一个本该退出的引擎继续活着；已完成的定时器/计划任务句柄也被当成活跃工作。现在只检查本进程认领的行与尚未完成的本地后台任务，不碰其他 owner 的行。
- **catalog 与 peer 读取只带元数据。** 会话列表快照过去会投影并传输消息历史，一次超时的快照就可能在另一个会话执行时把共享引擎拖死。现在 catalog 与 peer 读取只请求元数据，既不投影也不发送历史 —— 4 MiB 的 transcript 仍然保有完整快照，而元数据响应保持在 4 KiB 以内 —— 大 JSONL 帧也不再反复重扫已累积的全部内容。
- **引擎丢了就报成失败回合，而不是挂住。** 回放突发过去会在输出队列填满时终止引擎，现在改为等待有界容量。关闭时会明确排空并关闭输出接收端，即使桥接层还持有发送端克隆 —— 上一个版本在这里只会确认关闭却继续活着。引擎意外退出会为忙碌会话发布有序的实时失败与空闲状态，外壳因此不再展示一个已经不存在执行；不会凭空发明持久游标，也不会自动重试 provider 工作或工具。
- **只有 catalog 条目失败时，已打开的会话仍然可见**，而不是被列表丢掉。
- **长时间的前台命令不再被判为非法。** `bash` 与 `run_command` 工具把 `timeout_ms` 卡在 2 分钟，而产品侧的 TypeScript 工具接受 10 分钟，于是一个要跑三分钟的远程构建只得到一句 "invalid tool input"，模型只好重试同一条命令。上限现在放到 10 分钟，默认 2 分钟，与产品一致。
- **引擎的路由表按它实际发送的形状解码。** provider 路由以 snake_case 返回，按 camelCase 读取会静默得到空集或缺字段的路由。现在按 snake_case 解码，并在字段冲突或非数值时直接拒绝，而不是猜。
- **引擎自己生成的输入共用同一个身份。** 待处理 inbox 里只要有一条 monitor、wakeup、cron 或 job 通知，整页就会失败：投影把每个引擎输入 id 都当成付费提示词的 id 来解码。现在 inbox 读取、提升投影与回滚边界都从引擎落盘的 input id 派生同一个身份，通知在三个地方是同一个对象。
- **显式配置的上下文窗口在生成路由后仍然有效。** 只要宿主自己生成 provider 路由，显式配置的 native 上下文窗口就会被 catalog 里的窗口静默替换，`MIAO_CONTEXT_LIMITS=4000` 实际按模型完整窗口跑。生成的路由现在沿用显式配置，与操作者手写路由既有的优先级一致。
- **同一个 native 会话的并发创建会互相领养。** 两个请求都可能在产品投影为空时开始；若其中一个先发布了 Rust 放置，另一个走到 TypeScript 所有权栅栏时就会失败，而不是加入。现在只在这类放置冲突上重读并领养已有会话；绑定存在但没有投影会话的情况仍然失败。

## 外壳、App 与 CLI

- **运行状态收成一行。** 运行中的回合过去会重复 agent/模型信息、一行等待、一行扫描/计时/中断，再加一条状态行，把输入框垫在中间。现在固定一行显示当前阶段或工具活动、阶段已用时间、与阶段不同且放得下的回合时长，以及下一次 Escape 的作用；失败仍留在 transcript 里。
- **会话列表回到自己的范围。** 刷新与会话选择器调用 V2 列表 API 时丢了目录/项目范围，于是一次全局 catalog 读取就可能为无关项目与历史测试 storage 启动 native 引擎宿主。现在默认发送当前绝对目录，关闭目录过滤时发送当前项目，取不到项目身份时退回目录范围。
- **分页之后用量历史仍然可读。** 已结算的 provider 步骤作为持久事实保留，新增的分页接口给出模型归属、输入/输出/推理与缓存读写 token、费用和观测到的 TTFT。App 按这些事实画图，每根柱子区分未命中缓存的输入与缓存读写，模型或窗口变化时各自换算。
- **首页显示安装版本。** 安装版本现在渲染在首页 logo 下方；此前只出现在侧栏页脚和调试对话框里。
- **headless 运行保住自己的标题。** 很短的 `miao run` 可能在后台标题落盘之前就结束并关闭 runtime。现在显式的 Session 等待者会让该 Session 已有的标题工作结算完成，但不会接管模型工作，也不改变忙碌/空闲状态。
- **native 后台日志不再混进协议流。** native 后台 fiber 是在服务器的可观测层之外构建的，默认 logger 会把多行诊断写进 stdout —— 而那条流正是 ACP 编辑器当作 JSON-RPC 读取的。于是一次会话可能被一行后台标题日志污染。这些 fiber 现在走服务器日志层，真实的 `miao acp` 子进程交换可以跑完且每一帧都是合法 JSON-RPC。
- **MCP 工具保留真实名字。** native MCP 的别名会截断并清洗服务端与工具名，而按别名的第一个下划线反解，在名字很长或本身带下划线时会还原出错误的产品身份。现在把可信的原始身份直接写进持久历史，而不是再推导一次。
- **需要审批的紧凑工具调用绑定到它真正的目标。** 通过 `tool_call` 发现的扩展需要审批时，runtime 已经准备好了它真正的目标与参数，而 store 却拿这两者去和 wrapper 落盘的名称与输入比较，于是批准还没展示，运行就失败了。现在审批绑定在计划好的目标上：批准前不调用、接受后只派发一次、拒绝后不派发。
- **取消会话会取消它正在跑的钩子。** pre/post-tool 生命周期钩子拿到的是一个全新的取消令牌，而不是当前会话的令牌，因此操作者取消之后，钩子进程仍会一直跑到自己结束。现在钩子共用会话的令牌。
- **标题只生成并改名一次。** native 会话的空闲监听器与显式等待可能同时生成标题，而重复守卫对第二个请求立即返回，于是一个短命的 CLI 可能在改名落盘前就结束等待。现在标题工作按 storage 与 Session ID 围绕「生成 + 改名」整体合并，等待者通过这次持久改名加入。

## 构建、CI 与发布

- **单文件构建内嵌引擎。** 带 `--engine` 的构建把引擎二进制烘进可执行文件，启动时释放到候选发现会看的位置，因此全新安装不需要再单独 install-engine。已经装好且兼容的引擎仍然优先，内嵌副本只补空缺。
- **Windows 验证移到发布闸门。** Windows 的引擎与运行时套件不再在 PR 和 main 推送时运行；每夜的定时任务是早期预警，`release.yml` 针对确切的发布提交跑完整的 Windows 引擎套件，并且在它通过之前不允许发布。普通 PR 不再启动任何 Windows 作业，代价是只在 Windows 上出现的问题会推迟到夜间或发布时才暴露。
- **基准测试同时离开 PR 路径**：它每次推送都要占一个 runner，却不为合并把关。

## 验证与边界

每项改动都通过 `guard` 与聚合的 `ci-gate` 套件，包括 macOS 与 Linux 上的 Rust 引擎测试、TypeScript 单元/类型检查/e2e、会话黑盒回放以及 conformance harness。

- 发布提交上的 Windows 引擎套件是 Windows 唯一被保证对着已发布提交跑一次的地方；带这道闸门的第一个版本就是本版本。
- 对 0.3.7 编译候选的编辑器验收（Neovim 0.12.6 + CodeCompanion v20.0.1）在真实 UI 上通过了允许一次、拒绝与取消；它发现的更早一版协议故障 —— 后台标题日志写进 ACP stdout —— 就是上面那条修复。
- R13 与 R14 的 conformance 证据完整保留，包括 R13 那个失败的单元格 —— 它暴露的正是上面修掉的标题等待/改名竞态；全部证据文件都通过了 JSON 解析与凭证/私有主机扫描。
- Phase 2 的计划 —— 退掉第二套放置、把运行时收敛到单内核，以及在此之前必须先具备的能力 —— 记录在 `specs/rust-phase-2.md`。那是一份设计文档，不是本版本已交付内容的描述。
- 长时间运行的 watcher 宿主、集群放置，以及生产守护进程下的引擎回收，仍不在自动化证据范围内。
