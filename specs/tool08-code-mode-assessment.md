# TOOL-08:Code Mode 与批量调用的取舍

状态:评估完成;无代码改动。本文回答 TOOL-08 的三个验收问题:放弃原生 execute
(Code Mode)已接受了什么损失、`tool_search`/单调用/读批量的替代边界在哪、以及
"受约束组合调用"何时才值得试验。结论:**不建 Code Mode;维持现有替代面;试验的
重开条件挂在 VAL-01 任务基线上**。源码基线为 main `85efc79be8`,2026-10-30。

## 1. 现状盘点(as-is,锚定实现)

- **引擎没有组合调用入口**:工具面是单调用协议(一次一个 `tool_use`,一次一个
  结果),没有 code-mode/execute 批处理原语;`tools.rs` 的 `Prepared` 管线围绕
  单个调用的权限、审计与结算构建。
- **替代面已存在,且各自有界**:
  - **`bash`**(受限进程执行)就是"任意组合"的原生出口:数据转换、多命令管道、
    文件批量操作都在其中,且走完整权限/审批/沙箱边界——Code Mode 能做的"跑一段
    程序代替 N 个工具调用",bash 已经能做,还不用新建隔离执行环境。
  - **`tool_search`**(`tools.rs:1070`,`compact_disclosure` 开启时)把目录按需
    发现化,替代"把全部工具定义塞进系统提示"的体积损失。
  - **有界读批量**(ADR-13,`tests/read_batch.rs`):声明式只读并行,#1707 补齐了
    JOB-03 要求的真实重叠/墙钟收益/总成本测量,写入 `docs/measurements.md`。
- **损失清单(已接受)**:放弃 Code Mode 意味着——(a) 工具调用往返按次数计费,
  多步数据管道每步都有一次模型回合;(b) 无法在一个沙箱里连续变换中间态(中间
  结果落盘或进上下文);(c) 每个调用单独过权限。这三条损失在编码任务(VAL-01
  suite 的形态)里占比很小:真实开销主导是读放大与重试,不是调用次数。

## 2. 逐项回答

### 2.1 已接受损失与替代边界(验收 1)

见上节损失清单。替代边界:**结构化工具面(单调用)处理与工作区状态交互的一切;
bash 处理任意计算;`tool_search` 处理目录体积;读批量处理读放大**。四者合成后,
Code Mode 的增量场景只剩"多工具结果作为彼此输入的数据管道"——这类任务在当前
冻结的任务基线中没有出现。

### 2.2 何时试验受约束组合调用(验收 2)

不为"能力完整性"试验。重开条件(全部满足才立项):

1. VAL-01 的冻结任务基线扩入真实批量任务(数据整形、多文件重构管道),且
2. VAL-02 的按完成任务计量显示这类任务的费用/时长被**调度开销主导**(调用次数
   ×回合成本,而非模型推理本身),且
3. 设计先行:组合调用是**预声明脚本**(模型一次给出调用序列,引擎顺序执行),
   不是图灵完备的沙箱代码——后者就是 bash,不必重做。

### 2.3 若试验必须验证的契约(验收 3)

组合调用的设计约束在此记录,作为重开时的验收基线:调度开销计入报告;每个子调用
保留独立可追踪的结果与错误(不做整体 all-or-nothing);权限对每个子调用独立判定
(组合不得绕过单调用门槛);取消语义 = 停止后续子调用、已执行的按现状结算;超预算
(调用数/时长)有界并停止。

## 3. 结论

不建 Code Mode。现有替代面(bash + tool_search + 单调用 + 有界读批量)覆盖当前
冻结任务基线的全部形态;已接受的损失有清单、可量化,并在 VAL-01/VAL-02 的基线
给出量化的重开条件。TOOL-08 以本评估收口,不保留待办。
