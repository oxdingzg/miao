# MEDIA-04:语音输入与多媒体扩展取舍

状态:评估完成;无代码改动。本文回答 MEDIA-04 的三个验收问题:语音输入作为新候选的现实
形态、识别延迟/修正成本/隐私/费用的核验边界、以及"默认不引入常驻高负载"的约束是否成立。
结论:**不在终端内建语音输入**;语音作为输入通道的真实落点在多端线(移动客户端),终端用户
经由操作系统听写已免费获得该能力。源码基线为 main `890323d287`,2026-10-29。

## 1. 问题

MEDIA-04 把"语音输入"列为新候选,要求先验证识别延迟、修正成本、隐私与费用,并确认多媒体
扩展不引入常驻高负载。核心问题:语音输入在 miao 的产品形态(终端 TUI + 远程会话)里是否
存在一条值得实现的路径,还是应当归入其他工作线。

## 2. 现状盘点(as-is,锚定实现)

- **音频栈只有通知音效**:`packages/tui/src/audio.ts` 经 `@opentui/core` 的 `Audio` 播放
  预置提示音(`loadSoundFile`/`play`/`stopVoice`);`attention.ts` 是通知注意力系统。二者
  都是**输出**,没有捕获或识别路径。注意 `stopVoice` 停的是正在播放的音色(voice = 音色),
  与语音识别无关。
- **引擎明确无转录服务**:`crates/miao-engine/docs/media-workflow.md` 规定媒体观察走
  内建 skill → 受限 Bash 调 `ffprobe`/`ffmpeg` → `read_image` 读接触表;"Speech
  transcription remains dependent on tooling configured by the user, as in the shared
  skill"——转录依赖用户自配工具,引擎不内置。
- **无麦克风捕获代码**:全仓无音频捕获、语音活动检测或转写 API 调用。

即:现状没有任何语音输入能力;通知音效不代表语音能力,这与验收第 1 项的判断一致。

## 3. 终端形态的架构约束

miao 的 TUI 运行在 TTY 之上——本地终端、SSH、以及多端线的远程接入(mtty 移动客户端把
会话投递到远端设备)。这意味着:

- **进程没有音频设备访问权**。麦克风属于终端模拟器所在的设备,不属于跑在其中的 TUI
  进程;SSH 与串口会话连物理采集点都不存在。TUI 内建捕获在架构上不成立。
- **终端用户今天的语音输入路径已经存在**:macOS/Windows/各移动 OS 的系统级听写把文字
  直接"键入"任何有键盘焦点的应用,包括终端。这条路径零实现成本、零常驻负载、隐私由
  用户在 OS 层控制,且识别质量随 OS 升级自动改善。任何终端内建方案都无法超越它,只会
  复制一个更差的版本。
- 内建方案若要工作,唯一形态是**常驻音频栈**(采集、VAD、模型或 API 客户端),这直接
  违反 MEDIA-04 的第 3 项验收:默认不因语音或媒体扩展引入常驻高负载。

## 4. 候选路径评估

| 路径 | 延迟 | 修正成本 | 隐私 | 费用 | 判定 |
|---|---|---|---|---|---|
| OS 级听写(现状,零实现) | OS 内建,通常亚秒 | 文字已入输入流,常规编辑 | 用户在 OS 层自控 | 零 | **维持,不另建** |
| TUI 内建捕获 + 本地识别(whisper 类) | 可控 | 需自建修正 UI;终端编辑体验差 | 好 | 模型分发与常驻内存成本 | 架构不成立(TTY 无设备) |
| TUI 内建 + 云端转写 API | 一轮网络往返起步 | 同上 | 音频出域,需逐用户同意 | 按 API 计费,常驻客户端 | 架构不成立 + 违反无常驻约束 |
| 移动客户端内语音输入(mtty 多端线) | 移动 OS 原生听写或客户端内识别 | 移动输入法自带修正 | 客户端域内自控 | 原生听写为零 | **真实候选,归入多端线** |

识别延迟、修正成本与费用的**实测验证**只对移动客户端这条路径有意义,而它的验证归属
多端线的客户端验收(mtty 的移动目标),不属于终端条目的范围。

## 5. 结论

1. **不在终端做语音输入**。现状的 OS 听写路径已是终端形态下的最优解,内建方案要么
   架构不成立(TTY 无音频设备),要么违反无常驻负载约束。
2. **通知音效与语音能力正式区分**:audio.ts 是通知输出;本文与 media-workflow 的
   "无转录服务"边界共同确认,没有任何既有代码构成语音能力。
3. **语音输入的真实候选在多端线**:移动客户端(mtty)拥有麦克风与原生听写,若产品
   决定投入,应在多端线的客户端验收中立项重评;重开条件 = 多端线把语音列为输入通道
   的优先项。在那之前 MEDIA-04 以本评估收口,不保留待办。
4. **多媒体扩展的负载边界维持现状**:媒体观察按需调用 ffmpeg(用户工具),无常驻
   进程;音频栈仅在播放提示音的瞬间持有资源,`autoStart: false` 已保证按需启动。
